The problem: "it works on my machine"

😩 Without containers

• Trainer: Python 3.12, scikit-learn 1.6.1 — works.

• Learner A: Python 3.9 — pip install fails for NumPy 2.2.

• Learner B: scikit-learn 1.3 — InconsistentVersionWarning when loading the model, or worse, silently different behaviour.

• Server: no compiler, different OS libraries, wrong PATH.

🐳 With a container

• One image contains Python 3.12, pinned packages, the code and the model.

• Every machine with Docker runs the same bytes.

• "Install" becomes docker run churn-api.

• The image is versioned, stored and rolled back like any artifact.

Local Python vs virtual environment vs VM vs container

Compare the four ways to run the churn API
Your OS→System Python→all projects share packages

Fastest to start, but projects fight over package versions. Upgrading NumPy for one project can break another.

Your OS→Python→.venv per project

Isolates Python packages only (what we used on Day 1). The interpreter version, OS libraries and system tools still come from your machine.

Hardware→Hypervisor→Full guest OS + kernel→App

Strong isolation, but each VM boots a whole operating system: gigabytes of disk, minutes to start, lots of RAM.

Host OS kernel→Docker engine→Container: Python + packages + app

Isolates the whole user-space (interpreter, libraries, files, network, processes) but shares the host kernel. Starts in about a second; images are megabytes to a few hundred megabytes.

Image vs container

📀 Image

Like a class in Python, or a frozen installation disk. Read-only, versioned with tags (churn-api:1.0.0), shareable through a registry. Created by docker build or docker pull.

▶️ Container

Like an object created from the class. Has a state (running, exited), its own writable layer, network address and logs. Created by docker run. You can run many containers from one image.

Image layers and caching

Each Dockerfile instruction that changes the filesystem creates a layer. Layers are stacked, shared between images and cached: if an instruction and its inputs have not changed, Docker reuses the old layer instead of rebuilding it.

Build context

When you run docker build -t churn-api ., the final . is the build context: the folder whose files are sent to the daemon. COPY can only see files inside it, and .dockerignore decides what is left out. Run the command from the wrong folder and COPY app/ ./app/ fails because app/ isn't in the context.

Container lifecycle

Created — docker create (or the first half of docker run) prepares the container from the image but does not start the process.

The recipe

Dockerfile Fundamentals

A Dockerfile is a text file containing instructions that Docker uses to build an image. That image packages your application code, runtime, dependencies and configuration so the application runs consistently across environments. For our training project, we use a Dockerfile to package the FastAPI ML prediction API. A Dockerfile is code: version it in Git next to app/.

1 · How a Dockerfile works

📝 Dockerfile

The recipe. Plain text, read by docker build.

📀 Docker image

The result of the build: our API code, Python 3.12, the installed packages and the model, frozen and versioned.

▶️ Docker container

What docker run starts from the image: the live process serving /predict.

💡
The important distinction

The Dockerfile describes how to build the image; the container is created from that image. You never run a Dockerfile directly — you build it once, then run as many containers from the image as you need.

Rule of thumb

Use CMD when the image has one obvious default but you want to run other commands easily (debugging, one-off scripts) — that's our API. Use ENTRYPOINT when the image is a single tool and users only pass arguments. Always use the JSON (exec) form ["a", "b"] so signals like Ctrl+C and docker stop reach Uvicorn directly.

Explanation of the build sequence

👆 Click a step.

1 · FROM — selects the Python runtime: the official Python 3.12 image, slim Debian variant. Every later step builds on top of it.

Why copy requirements.txt first?

Docker caches build layers. If you change only app/main.py, Docker can reuse the dependency-installation layer instead of installing all packages again — rebuilds take seconds, not minutes. If requirements.txt changes, the dependency layer must be rebuilt. Try it in the layer cache simulator in Section 2.

Five habits of a good ML Dockerfile

🐍 Official Python base images

python:3.12-slim is maintained by the Docker and Python communities, receives security updates and has a predictable layout. slim drops compilers and docs; NumPy, SciPy and scikit-learn install from pre-built wheels, so we don't need them. Avoid alpine for data science — it uses musl and often forces slow source builds.

⚡ Dependencies before source

COPY requirements.txt → RUN pip install → COPY app/. Code changes many times a day; dependencies rarely. With this order the expensive install layer is reused (see the cache simulator in Section 2).

🙈 .dockerignore

Excludes .venv/ (hundreds of MB), .git/, caches, notebooks and .env from the build context: faster builds, smaller images, no accidental secrets.

📌 Pin versions

scikit-learn==1.6.1, not scikit-learn. An unpinned build next month may install a newer release whose pickles are incompatible with your churn_model.joblib. Pin the base image tag too (3.12-slim, never latest).

🔐
Never copy secrets into an image

Anything in an image layer can be extracted by anyone who can pull the image — even if a later instruction deletes the file. Do not COPY .env, API keys, cloud credentials or database passwords. Pass them at runtime with environment variables or a secret manager (Section 6 and 12).

The Dockerfile we use today

Our project Dockerfile is the minimal version plus four ENV settings for Python and pip, comments, and a COPY of just the model file rather than the whole models/ folder (so stray experiment files never end up in the image). Both versions start the same API.

# Customer Churn Prediction API — Day 2 container image
# Build from the project root (churn-api/):  docker build -t churn-api .

# 1. Base image: official Python image, slim Debian variant
FROM python:3.12-slim

# 2. Python behaviour inside containers
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1

# 3. All following paths are relative to /app inside the image
WORKDIR /app

# 4. Dependencies first: this layer is cached until requirements.txt changes
COPY requirements.txt .
RUN pip install -r requirements.txt

# 5. Application code and the trained model artifact
COPY app/ ./app/
COPY models/churn_model.joblib ./models/churn_model.joblib

# 6. Document the port the API listens on
EXPOSE 8000

# 7. Start Uvicorn, listening on all interfaces inside the container
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
  • FROM python:3.12-slimStart from the official Python 3.12 image (Debian slim). Everything else is added on top.
  • PYTHONDONTWRITEBYTECODE=1Don't write .pyc files — they are useless in a read-mostly container.
  • PYTHONUNBUFFERED=1Print logs immediately so docker logs shows them in real time.
  • PIP_NO_CACHE_DIR=1Don't keep pip's download cache inside the image — saves space.
  • PIP_DISABLE_PIP_VERSION_CHECK=1Skip pip's "new version available" network check during builds.
  • WORKDIR /appCreate /app and make it the current directory for later instructions and for the running container.
  • COPY requirements.txt .Copy only the dependency list first (into /app).
  • RUN pip install -r requirements.txtInstall the pinned packages. This is the slow, cache-worthy layer.
  • COPY app/ ./app/Copy the FastAPI package → /app/app/main.py, so app.main imports resolve from /app.
  • COPY models/churn_model.joblib ...Bake the trained artifact into the image at /app/models/ — exactly where app/main.py looks by default.
  • EXPOSE 8000Documentation for humans and tools; publishing happens with -p at run time.
  • CMD [...]Start Uvicorn on all interfaces, port 8000 (Section 4 explains 0.0.0.0).

Port mapping and why 0.0.0.0

Port-mapping simulatorBehaviour verified on a real Docker engine

Why 0.0.0.0?

Inside the container, 127.0.0.1 means the container itself. Docker forwards published traffic to the container's network interface, not its loopback. A server bound to 127.0.0.1 never sees that traffic. 0.0.0.0 means "listen on every interface", so forwarded requests arrive.

Host port vs container port

The container port is fixed by the app (Uvicorn's --port 8000). The host port is your choice — -p 8080:8000 serves the same API at http://localhost:8080. Two containers can both listen on 8000 internally but need different host ports.

Build-time vs runtime configuration

🏗️ Build time — baked into the image

Python version, installed packages, application code, the default model, defaults set with ENV. Changing these means docker build again.

🚀 Run time — supplied per container

Log level, which model file to load, service URLs, credentials, ports. Set with docker run -e, Compose environment:, or mounted files. The same image runs in dev, test and prod with different settings.

Run from the project root:
    uvicorn app.main:app --reload

    MODEL_PATH  path to the joblib artifact (default: models/churn_model.joblib)

import logging
import os
from contextlib import asynccontextmanager
from pathlib import Path
from typing import Any

import joblib
import numpy as np
from fastapi import FastAPI, HTTPException, status

from app.schemas import ChurnFeatures, HealthResponse, PredictionResponse

# Runtime configuration from environment variables (Day 2), with safe defaults.
LOG_LEVEL = os.getenv("LOG_LEVEL", "INFO").upper()

logging.basicConfig(
    level=LOG_LEVEL,
    format="%(asctime)s %(levelname)s [%(name)s] %(message)s",
)
logger = logging.getLogger("churn_api")

PROJECT_ROOT = Path(__file__).resolve().parents[1]          # .../churn-api
DEFAULT_MODEL_PATH = PROJECT_ROOT / "models" / "churn_model.joblib"   # same path as train.py
MODEL_PATH = Path(os.getenv("MODEL_PATH", str(DEFAULT_MODEL_PATH)))  # override with -e MODEL_PATH=...
FEATURE_ORDER = ["tenure", "monthly_charges", "support_calls"]

# Holds the loaded artifact. Filled once at startup, read by every request.
ml_artifacts: dict[str, Any] = {}


@asynccontextmanager
async def lifespan(app: FastAPI):
    """Load the model ONCE when the server starts; clean up on shutdown."""
    try:
        artifact = joblib.load(MODEL_PATH)
        if artifact["feature_names"] != FEATURE_ORDER:
            raise ValueError(
                f"Feature mismatch: model expects {artifact['feature_names']}, "
                f"API sends {FEATURE_ORDER}"
            )
        ml_artifacts.update(artifact)
        logger.info("Model v%s loaded from %s", artifact["model_version"], MODEL_PATH)
    except FileNotFoundError:
        logger.error("Model file not found at %s. Run: python training/train.py", MODEL_PATH)
    except Exception:
        logger.exception("Failed to load model from %s", MODEL_PATH)
    yield
    ml_artifacts.clear()
    logger.info("Model unloaded, server shutting down")


app = FastAPI(
    title="Customer Churn Prediction API",
    description="Serves a scikit-learn churn model trained on synthetic data (for learning only).",
    version="1.0.0",
    lifespan=lifespan,
)


@app.get("/")
def root() -> dict:
    return {"message": "Customer Churn Prediction API. Open /docs to try it."}


@app.get("/health", response_model=HealthResponse)
def health() -> HealthResponse:
    """Liveness: the process is running and can answer HTTP requests."""
    return HealthResponse(status="ok", model_loaded="model" in ml_artifacts)


@app.get("/ready", response_model=HealthResponse)
def ready() -> HealthResponse:
    """Readiness: the service can actually make predictions."""
    if "model" not in ml_artifacts:
        raise HTTPException(
            status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
            detail="Model not loaded",
        )
    return HealthResponse(status="ready", model_loaded=True)


@app.post("/predict", response_model=PredictionResponse)
def predict(features: ChurnFeatures) -> PredictionResponse:
    """Predict whether one customer will churn."""
    model = ml_artifacts.get("model")
    if model is None:
        raise HTTPException(
            status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
            detail="Model is not loaded. Run 'python training/train.py' and restart the API.",
        )

    # Build a 2-D array (1 row x 3 columns) in the SAME order used in training.
    row = np.array([[getattr(features, name) for name in FEATURE_ORDER]], dtype=float)
    logger.debug("Feature row sent to the model: %s", row.tolist())

    try:
        predicted_class = int(model.predict(row)[0])
        churn_probability = None
        if hasattr(model, "predict_proba"):
            class_index = list(model.classes_).index(1)        # column for "Churn"
            churn_probability = round(float(model.predict_proba(row)[0][class_index]), 4)
    except Exception:
        logger.exception("Prediction failed for input %s", features.model_dump())
        raise HTTPException(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            detail="Prediction failed due to an internal error.",
        )

    label = ml_artifacts["class_labels"][predicted_class]
    logger.info("input=%s prediction=%s prob=%s", features.model_dump(), label, churn_probability)

    return PredictionResponse(
        predicted_class=predicted_class,
        label=label,
        churn_probability=churn_probability,
        model_version=ml_artifacts["model_version"],
    )

Docker Compose Fundamentals

Docker Compose describes a multi-container application in a YAML file — images, builds, ports, environment, networks, volumes, health checks — and starts it with one command.

Why Compose?

Without Compose

Remember and retype: docker network create …, docker build …, docker run -d --name api --network … -p … -e … -e …, then the frontend, then MLflow… in the right order, on every machine.

With Compose

The whole setup is code in compose.yaml, reviewed in Git. docker compose up creates the network, builds images, starts services in dependency order and streams all logs.

Anatomy of a Compose file

name: churn-platform            # project name → prefixes containers and networks

services:                       # each service = one container configuration
  api:
    build: .                    # build an image from ./Dockerfile ...
    image: churn-api:1.0.0      # ... and tag it with this name
    ports:
      - "8000:8000"             # HOST:CONTAINER, quoted
    environment:
      LOG_LEVEL: INFO           # runtime configuration
    volumes:
      - ./models:/app/external-models:ro   # bind mount (or a named volume)
    healthcheck:                # how Docker decides the service is healthy
      test: ["CMD", "python", "-c", "..."]
    depends_on: []              # start-order relationships
    restart: unless-stopped     # what to do if it exits
    networks:
      - ml-net

networks:                       # user-defined networks (DNS by service name)
  ml-net: {}

volumes: {}                     # named volumes, declared once, used by services

Indent with spaces, never tabs (two per level). Keys end with :. List items start with - . Quote port mappings ("8000:8000"). Validate any time with docker compose config.

Startup order is not readiness

Plain depends_on: [api] only waits until the api container has started — the model may still be loading, so the client's first request can fail.

depends_on: {api: {condition: service_healthy}} waits until the api's health check passes — i.e. /ready returns 200 because the model is loaded. This uses the readiness endpoint we built on Day 1.

Even so, clients should retry: a service can become unhealthy later. Our smoke test retries /ready up to 10 times.

"""Smoke test that calls the churn API from ANOTHER container.

Used by the "api-client" service in compose.yaml. It reads the API address
from the API_URL environment variable, waits until /ready answers 200,
then sends one prediction request. Only the Python standard library is used,
so it runs in the plain python:3.12-slim image.
"""
import json
import os
import sys
import time
import urllib.error
import urllib.request

API_URL = os.getenv("API_URL", "http://localhost:8000")
CUSTOMER = {"tenure": 12, "monthly_charges": 85.5, "support_calls": 3}


def wait_until_ready(attempts: int = 10, delay: float = 2.0) -> None:
    for attempt in range(1, attempts + 1):
        try:
            with urllib.request.urlopen(f"{API_URL}/ready", timeout=3) as response:
                print(f"[api-client] GET {API_URL}/ready -> {response.status}", flush=True)
                return
        except (urllib.error.URLError, ConnectionError) as exc:
            print(f"[api-client] attempt {attempt}/{attempts}: not ready ({exc})", flush=True)
            time.sleep(delay)
    sys.exit(f"[api-client] API at {API_URL} never became ready")


def predict() -> None:
    request = urllib.request.Request(
        f"{API_URL}/predict",
        data=json.dumps(CUSTOMER).encode("utf-8"),
        headers={"Content-Type": "application/json"},
        method="POST",
    )
    with urllib.request.urlopen(request, timeout=5) as response:

Production Concepts and Recap

Today's setup is correct for learning and development. Production adds hardening and automation — introduced here, implemented progressively in later sessions.

Production concepts

📉 Image size optimisation

Slim bases, PIP_NO_CACHE_DIR, a tight .dockerignore, only runtime dependencies (tests stay out), and multi-stage builds when compilers are needed. Smaller images pull faster and have fewer vulnerabilities.

📌 Dependency pinning

Exact == pins today; next step is a full lock file (pip freeze > requirements.lock or pip-tools) covering transitive packages, and pinning the base image by digest (python:3.12-slim@sha256:…).

👤 Non-root containers

Our image runs as root. If an attacker breaks into the process, root inside the container makes escalation easier. Create a user and switch with USER (example below).

🔐 Secret management

Runtime injection from a secret manager (cloud secret stores, Vault, Docker/Compose secrets). Never in images, Git or logs.

📈 Logging & monitoring

Log to stdout/stderr (we do); a platform ships logs to a central store. Add metrics (latency, error rate, prediction distribution) and alerts; ML adds data-drift monitoring.

❤️ Health checks & restarts

Liveness /health, readiness /ready, Docker HEALTHCHECK or Compose healthcheck, plus restart: unless-stopped so crashed services come back.

🏬 Image registries

Push versioned images (churn-api:1.0.0, git SHA tags) to Docker Hub, GitHub Container Registry or a cloud registry; servers pull exactly that version.

🤖 Basic CI/CD

On every push: install, train/fetch the model, run tests, build the image, push it to the registry. Deployment then pulls the tested image.

🔎 Troubleshooting checklist

🎤 Interview questions with model answers

1. What is the difference between a Docker image and a container, and how do layers make builds fast?

An image is an immutable, versioned template made of stacked read-only layers plus metadata (command, ports, environment). A container is a runtime instance of an image with its own writable layer, process, network identity and lifecycle. Each Dockerfile instruction produces a layer that Docker caches; if an instruction and its inputs are unchanged, the cached layer is reused. Ordering the Dockerfile from rarely to frequently changing steps — dependencies before source code — keeps the expensive install layer cached.

2. How would you containerise a FastAPI model-serving application?

Start from an official slim Python image, set a working directory, copy and install pinned runtime requirements first, then copy the application package and the model artifact (or load the model at runtime from a registry or volume). Run Uvicorn in exec form bound to 0.0.0.0 on a known port and document it with EXPOSE. Add a .dockerignore, keep secrets out, ideally run as a non-root user, and expose liveness/readiness endpoints for health checks. Make sure the model was produced with the same library versions installed in the image.

3. A container exits immediately after starting. How do you debug it?

docker ps -a for the status and exit code (1 = application error, 127 = command not found, 137 = killed/out of memory). docker logs for the traceback. docker inspect for the effective command, environment, mounts and ports. To look inside, run the image with an overridden command, e.g. docker run --rm -it image sh, and check paths and packages. Typical fixes: correct the module path (app.main:app), install a missing dependency, fix a wrong file path or environment variable.

4. Why can't one container reach another on localhost, and how does Docker Compose solve service discovery?

Each container has its own network namespace; localhost refers to that container only. Compose places services on a shared user-defined network with an embedded DNS server, so each service name resolves to the right container IP. Services call each other by name (http://api:8000) and the URL is injected as configuration. Published ports are only needed for traffic from the host or outside.

5. Bake the model into the image or load it at runtime? What are the trade-offs?

Baking it in gives an immutable, self-contained artifact: image version equals model version, deployments and rollbacks are trivial, and nothing external can fail at start-up — good for stable models and demos. Loading at runtime (volume, object storage, model registry like MLflow) decouples model releases from code releases and suits frequent retraining, but requires tracking which model each instance serves, access to the store, and readiness checks that reflect model loading. Either way, library versions in the image must match those used for training.
